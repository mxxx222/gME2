## 2. Architecture options and recommendation

### Options considered

1. **Recommended: one TypeScript modular-monolith API with PostgreSQL.** Retain the React/Vite SPA and add a versioned same-origin JSON API in the same repository and deployable application boundary. Use a modest Node.js TypeScript server (Fastify is a suitable default), PostgreSQL with versioned SQL migrations, and parameterized queries. Keep domains separated in modules, not services. A managed PostgreSQL service can reduce routine operations, but select its provider only after residency, budget, and hosting requirements are known.
2. **Managed backend platform (database/auth/API bundled).** Fastest initial delivery and less server operations, but introduces a provider-specific auth/data authorization model. It is suitable if its region, privacy terms, row-level authorization, export/deletion, backup, and exit/migration story meet requirements. Do not choose one before those requirements are known.
3. **Separate services or a custom multi-service architecture.** Not justified by the current small SPA, absence of independent workloads, or scale evidence; it adds deployment, observability, and security boundaries without a current benefit.

The first option reuses the repository's TypeScript/npm toolchain and keeps authorization, consent, and persistence behavior explicit in a testable server boundary. PostgreSQL transactions, foreign keys, uniqueness constraints, and migrations suit account-owned progress and invitation state. It avoids rewriting the frontend and allows a later move to managed platform services or separate components behind stable API contracts. A managed platform remains a credible alternative if operational capacity is the dominant constraint.

**Authentication is an approval gate, not an implementation assumption.** Before building account flows, compare an established external identity provider, a provider plus an application session, and a managed backend's integrated auth against login methods, recovery, cost, region/data-processing terms, revocation, deletion, and exit options. Prefer an established provider over implementing password handling. The backend must validate provider-issued identity; do not invent a hybrid token/session scheme to defer this choice. Select whether the browser uses provider-managed secure cookies or a backend-for-frontend session only after confirming the chosen provider's supported flow and operational responsibilities. No provider is selected in this proposal.

## 3. Data model proposal

IDs should be opaque UUIDs generated server-side. All user-owned rows carry `user_id`; the API derives it from the authenticated session. Do not store intimate free text. Treat even categorical progress and partner-link metadata as sensitive behavioral data because they reveal use of a relationship-wellbeing product.

| Entity | Purpose, fields, PK and relationships | Ownership, authorization, indexes, sensitivity, retention and deletion |
|---|---|---|
| `users` | Account identity mapping. PK `id`; unique `auth_subject`; `created_at`, optional `deleted_at`. No profile fields by default. | Account service only; owner gets a minimal self-view. Unique index on `auth_subject`. High sensitivity (identity). Delete or irreversibly pseudonymize on account deletion; keep a tombstone only if essential to finish deletion safely. |
| `challenge_progress` | One current completion per activity per user and challenge. Composite PK `(user_id, challenge_id, activity_id)`; FK `user_id → users.id`; `completed_at`. This matches current idempotent completion behavior and does not preserve repeat history. Challenge definitions remain bundled/versioned until authoring requires DB storage. | Only the owning user; no partner access. Index `(user_id, challenge_id)` and optionally `(user_id, completed_at)`. Sensitive behavioral metadata. Retain while account is active; delete with account. If product semantics later require repeat history, migrate to separate completion records with stable IDs and timestamps rather than silently changing this row's meaning. |
| `user_preferences` | **Not needed initially.** If cross-device prompt length is requested: PK/FK `user_id → users.id`, typed preference fields, `updated_at`. | Owner-only. `user_id` PK provides lookup. Low-to-medium sensitivity; retain only current explicit settings and cascade-delete with account. No inferred interests. |
| `auth_sessions` | If the API maintains sessions: PK `id`; FK `user_id → users.id`; unique `token_hash`; `created_at`, `expires_at`, `last_seen_at`, optional `revoked_at`. Never store the cookie bearer value. | Server-only. Index `token_hash` for lookup and `expires_at` for cleanup. High sensitivity (credential-equivalent metadata). Revoke on logout/security events, cascade on account deletion, and purge expired rows. |
| `privacy_consents` | Only when a separate optional purpose exists. PK `id`; FK `user_id → users.id`; `purpose`, `notice_version`, `decision`, `recorded_at`, optional `withdrawn_at`. | Server-only audit access. Index `(user_id, purpose, recorded_at)`. Sensitive preference/consent metadata. Retain only as long as necessary to evidence the decision, subject to legal review; delete or pseudonymize under the documented deletion policy. |
| `partner_invitations` | Later only. PK `id`; FK `inviter_user_id → users.id`; hash of random high-entropy token; state and creation/expiry/used/revoked timestamps. No preference or progress payload. | Inviter may view/revoke own pending invite; redemption is server-side. Unique token-hash index; indexes for inviter/state and expiry cleanup. High sensitivity (relationship metadata). One-time, short expiry; purge after expiry/acceptance and a defined abuse/audit window; delete on account deletion. |
| `partner_relationships` and membership | Later only. Relationship PK `id`; status, `created_at`, `ended_at`. Membership composite PK `(relationship_id, user_id)` with FKs to relationship and `users`, plus `joined_at`, `left_at`. | Members see relationship existence/status only, not each other's private progress. Both accept; either can leave. Unique active-membership constraints and index by member. High sensitivity. End access immediately on leave; remove memberships/relationship under a defined policy and account-deletion flow. |
| `sharing_grants` | Later only. PK `id`; FKs `relationship_id`, `granting_user_id → users.id`; `scope`, `granted_at`, `revoked_at`, `notice_version`. | Only the granting owner and authorization service. Index active grants by relationship and owner. High sensitivity. Deny by default, revoke on relationship end, cascade/remove on account deletion, and retain only necessary audit evidence. |
| `referral_attributions` | Later only. PK `id`; opaque referral-code hash; optional FK attributed `user_id → users.id`; campaign identifier, `created_at`, `expires_at`, attribution policy. Never store referrer email or raw token. | Minimal service-only access. Unique code-hash index; expiry and attribution lookup indexes. Medium sensitivity (pseudonymous acquisition metadata). Short retention; delete on expiry or account deletion. |
| `analytics_events` | **Not needed for MVP.** Prefer aggregate operational counters. If justified later: PK event ID, allowlisted event name, coarse timestamp, optional pseudonymous user key only with consent, schema version. | Analytics service only; no prompts, reflections, sensitive identifiers, referral token, or partner content. Index by event/time only as needed. Pseudonymous personal data remains sensitive. Short TTL; delete or irreversibly aggregate on expiry/account deletion. |

**Entity decisions:** profiles, free-text activity history, individual solo-session history, analytics events, referrals, and partner tables are not justified for the first persistence slice. A separate audit trail should record security/administrative events with minimal metadata, not content, and use a defined short retention period.

**Completion contract:** a supported challenge/activity pair may be marked complete once for each account; repeating the completion request is idempotent and preserves the original completion timestamp. Activities may be completed in any order, matching the current UI. Validate both IDs against the supported, versioned application catalog; reject unknown IDs. The first release does not record attempts, repetitions, reflections, or session history.

## 4. Proposed API boundaries

All routes are HTTPS, same-origin, versioned `/api/v1`, schema-validated, and authenticated except explicitly public invite/referral resolution endpoints. Return generic errors that do not disclose account existence; use stable error codes and request IDs. Never trust a client `user_id`.

| Boundary | Example operations | Authorization |
|---|---|---|
| Session/account | `GET /me`, `POST /session/logout`, `GET /me/export`, `DELETE /me` | Authenticated identity/session; data scoped to session user; deletion requires recent re-authentication and CSRF protection. Login/callback endpoints depend on the selected identity provider. |
| Challenge catalog/progress | `GET /challenges`, `GET /me/challenges/{challengeId}/progress`, `PUT /me/challenges/{challengeId}/activities/{activityId}` | Catalog can be public; progress read/write requires authentication and derives user from session. Validate IDs against supported challenge/activity version; completion is idempotent and has no reflection field. |
| Preferences/consent (if needed) | `GET /me/preferences`, `PATCH /me/preferences`, purpose-specific consent create/withdraw | Owner-only; accept a strict allowlist of fields/purposes; withdrawal must take effect immediately for future processing. |
| Partner invitations/relationship/sharing | **No partner endpoints in the first release.** Later API boundaries require a separately approved product scope. | Do not introduce partial sharing logic. If approved, creator-only invite management, one-time expiring token, authenticated acceptance, and per-owner explicit grants; re-check active relationship and grant on every read. |
| Referral (later) | Resolve opaque code at landing; attach eligible attribution on account creation | Public resolution reveals no user identity; rate-limited, random codes, expiry and replay/abuse controls. |
| Analytics | No client endpoint initially | If introduced, allowlisted event schema, opt-in enforcement, server-side minimization and aggregation; never accept arbitrary payloads. |

## 5. Security, privacy, and operations

| Threat / risk | Required controls |
|---|---|
| Cross-account access / IDOR | Derive owner from authenticated identity/session, scope every query by owner, enforce FK/constraints, deny by default; integration tests must attempt other-user read/write/export/delete. Opaque IDs are not authorization. |
| Unauthorized partner access | No partner API or shared access in the first release. If later approved: bilateral acceptance plus separately scoped grants from each owner; authorization check on every request; revocation/leave immediately blocks subsequent reads. |
| Leaked invitation | High-entropy one-time token, store only hash, short expiry, revoke endpoint, avoid tokens in logs/referrers/analytics, generic responses, require explicit recipient acceptance; never place private data in invitation URL. |
| Session theft / CSRF | TLS; `Secure`, `HttpOnly`, `SameSite` cookies; server-side revocation and expiry; rotate on authentication/privilege changes; CSRF token/origin checks on state-changing requests; no tokens in localStorage. |
| Enumeration and abuse | Generic login/invite responses; server-side layered per-IP and per-account limits; progressive throttling for login, invite creation/redemption, referrals and export; monitoring without logging sensitive payloads. |
| Rate-limit bypass | Do not trust client-supplied identity or arbitrary forwarded-IP headers; honor proxy headers only from configured trusted proxies. Combine per-IP and per-account quotas, with shared counters if the API is horizontally scaled. |
| Injection / mass assignment | Parameterized SQL, schema validation, strict field allowlists, output encoding, safe migrations; never interpolate SQL or accept arbitrary client objects as DB updates. |
| Analytics leakage | No product events at first; never collect prompt/check-in text or partner details; explicit separate opt-in, allowlisted fields, pseudonymization, retention limits, restricted access and deletion path. |
| Referral abuse | Random short-lived codes, no email disclosure, one attribution policy, replay limits, rate limits and anomaly monitoring; do not reward or expose attribution until abuse requirements are defined. |
| Improper deletion / backups | Start an idempotent deletion workflow that immediately marks the account non-active and revokes sessions/access, then removes owned data and coordinates external identity-provider deletion where supported. Define provider backup expiry and ensure restores cannot reactivate deleted accounts (for example, replay deletion tombstones); test deletion, export, and restore. Any retained records need a documented purpose and expiry. |
| Secrets / development configuration | Keep credentials out of Vite `VITE_*` variables and source control; server-only secret manager/env injection; `.env` ignored; separate dev/staging/prod credentials and least privilege; no production data in local fixtures. |
| Sensitive data exposure | Do not persist free text or session duration by default; encrypt transport and managed DB/backups at rest; redact logs; restrict operator access; define access review and incident response. |

**Privacy requirements:** state the 18+ check accurately as self-attestation unless a legal/product review requires stronger age assurance; do not collect birth date/documents by default. Publish an accurate notice for hosting, identity, database, email, backup, and any later analytics. Define purpose and lawful basis, retention, export, deletion, backup expiry, and contact path before launch. Complete jurisdiction-specific legal review; relationship/intimacy usage can be highly sensitive even when prompts are nonsexual. Consent must be granular, informed, optional, and withdrawable for partner sharing and any optional analytics. A privacy notice acknowledgement is not itself consent.

**Authentication, authorization, and consent are separate:** authentication establishes who made a request; authorization decides whether that principal may access the resource; consent records agreement to a particular optional use or disclosure. None implies either of the others. In particular, an authenticated user may read their own progress without granting partner access. The first release has no partner endpoints.

**Abuse and reliability:** validate server-side; use same-origin deployment to avoid permissive CORS; configure security headers and CSRF protection; cap request sizes; return redacted structured errors; health/readiness checks; alert on auth, migration, and DB failures. Use database transactions where operations are local; use an idempotent workflow/outbox or equivalent state machine for account deletion that spans an external identity provider. Add background workers only when a verified asynchronous requirement exists.

**Schema evolution, deployment and recovery:** version every schema change with ordered migrations; test from an empty database and the immediately prior supported schema; prefer additive, backward-compatible changes, and separate destructive changes behind an explicit reviewed migration. Do not run destructive migrations at application startup or silently discard existing user data. Document failed-migration recovery and backup restore before launch. Keep static frontend and API in one deployable boundary initially; use managed PostgreSQL only after region and contract review; apply migrations as an explicit release step; separate least-privilege runtime and migration credentials; use encrypted automated backups and a tested restore/retention schedule. No production hosting, deployment, backups, or infrastructure are configured in this repository.

## 7. Decisions that require product input

1. **Approved direction:** optional account-backed cross-device challenge progress, with anonymous use preserved and no automatic import. The identity/session choice still blocks account implementation.
2. Are partner invitations and shared progress in the first backend release? If yes, which exact progress fields can each person see, and must sharing be independently granted per category?
3. Which jurisdiction(s) and launch market govern age assurance, data residency, legal basis, and retention? The present 18+ checkbox is self-attestation only.
4. Which identity provider/authentication UX and account recovery policy are acceptable (for example, verified email link versus another supported method), and what operational/data-processing constraints apply to the vendor? This is a blocking approval before account implementation; session handling must follow the selected provider's supported design.
5. Is product analytics/referral attribution necessary at launch? Default recommendation: neither; revisit only with a defined purpose, consent and retention policy.

Defaults that are reversible and low-risk: retain React/Vite; use a same-origin modular monolith and PostgreSQL; make progress private and server-authorized; persist activity completion only; keep reflections, solo timer telemetry, product analytics, partner sharing, and referrals out of the initial vertical slice.
